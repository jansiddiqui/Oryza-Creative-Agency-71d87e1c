# Client operations (Phase 4A): setup and how it works

Clients, monthly plans, the master calendar, the Today view and deadlines now live inside `/admin`, using the same
sign-in, allow-list, Row Level Security and activity log as before. Everything is rule-based: there are no AI calls.
Plans are generated by the website's own planner code, so a client's plan matches what the plan builder shows.

## 1. Run the migration (once, about 2 minutes)

You need the first migration (`20261020000001_admin_foundation.sql`, see `docs/supabase-setup.md`) already run.

1. Supabase dashboard → your project → **SQL Editor** → **New query**.
2. Open `supabase/migrations/20261101000001_client_ops.sql` from the repo, copy **all** of it, paste it and click **Run**.
   You should see "Success. No rows returned".
3. Check **Table Editor**. These new tables exist, each with **RLS enabled**:
   `clients`, `client_plans`, `content_items`, `tasks`, `shoot_days`, `onboarding_items`, `team_members`,
   `deadline_rules` (34 rows of default rules) and `ops_settings` (one row: working days Mon–Sat).
4. Optional check: SQL Editor →
   `select format, step, offset_days from deadline_rules where format = 'reel' order by sort;`
   should list script −5, shoot −3, edit −2, client approval −1, schedule −1, publish 0, post-check +1.

Run it once. Nothing in the first migration is changed or deleted, except one thing: the activity-log action list is
widened to include the new client actions.

*(With the Supabase CLI instead: `npx supabase db push`, which applies the new file in order.)*

No new keys or Vercel settings are needed. Deploy the branch after the migration has run (the new admin pages expect
the tables to exist).

## 2. First steps in the admin

1. **Settings** (owners only) → **Team**: give each person their roles (strategist, designer, shooter, editor,
   community manager) and working days, then **Save**. New tasks go to the first active person with the matching role.
2. **Settings** → **Working days** (default Mon–Sat) and **Deadline rules**, if you want to change the defaults.
3. **Leads** → open a lead → **Convert to client**:
   - Plan-builder leads bring their answers. Other leads get the category questions in the form.
   - Choose the package and the start date, then **Create client and generate plan**.
4. In the **plan editor** you can:
   - edit titles, hooks, calls to action and times
   - move, remove or add items
   - assign people

   Then press **Approve plan**. This creates the content items, their tasks and the shoot days.
5. Use **Today** each morning and the **Calendar** for the whole month.

## 3. Rules the system follows

**Deadlines**: each step is worked back from the publish date (D):

| Format | Steps |
| --- | --- |
| Reel | Script D-5 · Shoot: the nearest shoot day on or before D-3, otherwise "Client sends footage" D-4 · Edit D-2 · Client approval D-1 · Schedule D-1 · Publish D · Post-check D+1 |
| Post / carousel | Copy D-4 · Design D-3 · Client approval D-1 · Schedule D-1 · Publish D |
| Story | Prepare D-1 · Publish D |
| Other formats | Shorts, videos, blogs, Google posts, broadcasts, WhatsApp status, events and pins have their own short defaults; anything else gets Prepare D-1 · Publish D |

- **Working days:** only working days count. A due date that falls on a day off moves to the working day before it.
  The publish date itself never moves.
- **Late tasks:** a task that is already past due when the plan is approved is saved as **late** and flagged.
- **Moving an item:** its open tasks are recalculated; tasks already done stay as they were. If the client has
  already approved the item, the admin is asked to confirm first.
- **Compliance notes:** compliance notes from the plan stay attached to each item and to the plan, and **cannot be
  edited or removed**. The database refuses the change too, even with the service role.
- **Wording warnings:** the plan editor warns when edited text breaks the category's wording rules (the same checks
  the plan engine uses, such as "best", "guaranteed" or cure claims for clinics).

## 4. Who can see and do what

| | Visitors (not signed in) | Signed-in non-admin / switched-off admin | Editor | Owner |
| --- | --- | --- | --- | --- |
| Clients, plans, items, tasks, shoots, onboarding | nothing | nothing | read + edit | read + edit |
| Deadline rules, working days, team roles | nothing | nothing | read | read + edit |

Every change is written to the activity log (**Activity**, and the Activity section of each client page).

## 5. Check it works

1. **Leads** → **Convert to client** on a test lead. The plan editor opens with a draft plan.
2. Change a hook to include "best". A "Check wording" warning appears.
3. **Approve plan**. The message shows how many items, tasks and shoot days were created.
4. **Calendar**: the items show in the client's colour. Drag one to another day (or tap it → **Move**); its tasks move with it.
5. **Today**: tasks are grouped into Overdue · Due today · Next 3 days, with Publishing today and Shoots today.
6. Sign out and open `/admin/calendar`. It redirects to the login page.
